## 2. 关键架构判断（逐条结论）

### 2.1 本地存储选型（Q1）

- **结论**：Room `2.8.4`，注解处理用 **KSP**（`com.google.devtools.ksp` 插件，版本 `2.2.21-2.0.4`，与 Kotlin `2.2.21` 严格对应），**不使用 kapt**。
- **兼容性核对**：Room 2.8.x 的 `minSdk` 为 **API 23**（≤ 本工程 minSdk 24）；它属于 Jetpack 库，**不与 SDK 版本强耦合**，不存在 core-ktx 1.19.0 那种 `minCompileSdk=37` 的 AAR 元数据约束；Room 2.8.0 起要求的 Room Gradle Plugin 最低 AGP 为 8.4（本工程 AGP 8.13.2 ✓）。KSP `2.2.21-2.0.4` 为官方为 Kotlin 2.2.21 发布的对齐版本 ✓。
- **Schema 导出策略**：使用 KSP 参数 `room.schemaLocation` 导出 JSON schema，**提交仓库**，用于后续迁移与 `room-testing` 的迁移测试；不启用 Room Gradle Plugin（少一个插件，降低接入风险，二者二选一即可）。
- **被否决**：`kapt`（慢、已不推荐）；`sqlite` 裸接口（无编译校验、样板多）；纯文件/键值存储（无法支撑递归位置树与多对多）。

### 2.2 多对多「存放关系」的物理实现（Q2，本设计最重要点）

**为什么不能退化成 `Item.locationId` 一对多**：
1. [PRD 08 数据字段业务语义](../prd/08-数据字段业务语义.md) §7.3 明确「一件物品可关联多个存放位置」，如「10 卷胶带 5 卷在厨房、5 卷在储物间」——一对多无法表达分摊。
2. `Placement` 携带 **该处数量 / 该处备注 / 该处最后确认时间** 三个**关系级属性**；一对多只能把这些挤进物品行，语义错误（一处确认 ≠ 整件确认）。
3. 删除/移动位置时，一对多需要重写物品的单一 `locationId`，无法表达「只把储物间那箱移走，厨房那卷不动」。
4. 后期改为一对多→多对多的迁移成本极高（需拆行、补关系级字段），违反「一次到位」。

**三张核心表定义**（完整字段见 [04-数据结构与接口.md](04-数据结构与接口.md)）：

`item`
| 字段 | 类型 | 键/约束 | 说明 |
|---|---|---|---|
| `id` | TEXT | **PK**（UUID） | 应用生成 |
| `name` | TEXT | NOT NULL | 名称（允许同名） |
| `normalizedName` | TEXT | — | 归一化名称（检索用） |
| `pinyinFull` | TEXT | — | 名称+别名全拼（空格分隔，检索用） |
| `pinyinInitials` | TEXT | — | 名称+别名首字母（检索用） |
| `aliasBlob` | TEXT | — | 归一化别名拼接（子串检索用） |
| `categoryId` | TEXT | **FK→category** `ON DELETE SET NULL`，**索引** | 未填=未分类 |
| `status` | TEXT | **索引** | `ItemStatus.code` |
| `quantity` | INTEGER | NOT NULL DEFAULT 1 | 仅整数 |
| `note` | TEXT | 可空 | — |
| `createdAt` | INTEGER | NOT NULL | epoch millis UTC |
| `lastModifiedAt` | INTEGER | NOT NULL | 最后变动时间 |
| `lastConfirmedAt` | INTEGER | 可空，**索引** | 最后确认时间 |

`location`
| 字段 | 类型 | 键/约束 | 说明 |
|---|---|---|---|
| `id` | TEXT | **PK**（UUID） | 内置项用固定哨兵 UUID |
| `parentId` | TEXT | **FK→location** `ON DELETE RESTRICT`，**索引** | 根为空 |
| `name` | TEXT | NOT NULL | — |
| `typeTag` | TEXT | 可空 | 视觉标记，无强约束 |
| `isTemporary` | INTEGER | NOT NULL DEFAULT 0 | 临时/待归位区 |
| `isBuiltIn` | INTEGER | NOT NULL DEFAULT 0 | 内置不可删 |
| `note` | TEXT | 可空 | — |
| `sortOrder` | INTEGER | NOT NULL DEFAULT 0 | — |
| `path` | TEXT | NOT NULL，**索引** | **物化路径**（ID 序列 `/a/b/leaf/`，含自身） |
| `depth` | INTEGER | NOT NULL | 根=0，冗余便于校验 |
| `createdAt` | INTEGER | NOT NULL | — |

唯一约束：`UNIQUE(parentId, name)`（同一父级下不重名，软校验的物理兜底；根级用 `parentId IS NULL` 参与，SQLite 对 NULL 不判重，故根级重名由应用层兜底，见 [09-待明确事项.md](09-待明确事项.md) A-3）。

`placement`（多对多关联）
| 字段 | 类型 | 键/约束 | 说明 |
|---|---|---|---|
| `itemId` | TEXT | **复合 PK**，**FK→item** `ON DELETE CASCADE`，**索引** | — |
| `locationId` | TEXT | **复合 PK**，**FK→location** `ON DELETE CASCADE`，**索引** | — |
| `isPrimary` | INTEGER | NOT NULL DEFAULT 0，**索引** | 主位置标记 |
| `quantity` | INTEGER | 可空 | 该处数量；空=继承物品总数量 |
| `note` | TEXT | 可空 | 该处说明（「侧袋里」） |
| `lastConfirmedAt` | INTEGER | 可空 | 该处最后确认时间 |
| `createdAt` | INTEGER | NOT NULL | — |

**主位置唯一——双层保证**：

1. **数据库层（安全网，物理不可破坏）**：部分唯一索引
   `CREATE UNIQUE INDEX IF NOT EXISTS index_placement_primary ON placement(itemId) WHERE isPrimary = 1;`
   该索引在 `ShounaDatabase.Callback.onCreate()`（以及未来每个迁移脚本）中用原始 SQL 创建，**不在 `@Entity(indices=...)` 中声明**（Room 的 `@Index` 不支持 `WHERE` 部分索引）。SQLite 3.8.0+（API 24 自带 3.9.2）支持部分索引 ✓。Room 不会因「多出一个未声明的索引」而校验失败（Room 只校验已声明对象是否存在，不禁止额外索引）。
2. **应用层（主机制 + 事务）**：`PlacementDao.setPrimary(itemId, locationId)` 标注 `@Transaction`，执行**同事务两条语句且顺序固定**：
   - ① `UPDATE placement SET isPrimary = 0 WHERE itemId = :itemId`
   - ② `UPDATE placement SET isPrimary = 1 WHERE itemId = :itemId AND locationId = :locationId`
   先全清 0 再置 1，避免中间态触发部分唯一索引冲突；原主位置在此过程中**自动降级**。

**「至少一个主位置」不变式**：由 Repository 保证——
- 新建物品首条 `placement` 强制 `isPrimary=1`（无位置则落到内置「未指定位置」且为主）；
- 删除一条主 `placement` 时：若该物品还有其他 `placement`，同事务把**最早创建的一条**提升为主；若无，则补建指向内置「未指定位置」的主 `placement`；
- 物品失效（已丢弃/已送人/已用掉）时 `placement` **保留**，仅在常规查询中过滤（[PRD 08 数据字段业务语义](../prd/08-数据字段业务语义.md) §7.3）。

### 2.3 搜索方案（FR-19/20/21/22，NFR-05/06）

- **结论**：采用 **「Room 全量投影 → 内存归一化索引」**，**不采用 Room FTS4/FTS5**。
- **否决 FTS 的具体理由**：
  1. 需求是**中文子串包含**（`name contains q`）。FTS 的 `unicode61` 分词器把整段连续中文当作**单个 token**，只能做前缀 `token*` 匹配，**无法命中「电风扇」中的「风扇」**。
  2. 能做子串的 `FTS5 trigram` 分词器需要 SQLite ≥ 3.34，且 Android 打包 SQLite 的 FTS5 可用性因版本而异，**API 24 上不可靠**（本工程 minSdk 24）。
  3. 需求还要**跨字段混排**（名称前缀 > 名称子串 > 别名/拼音 > 位置/分类/标签），FTS 的 `bm25` 排序无法表达这套**业务权重**，仍需应用层重排，等于 FTS 白做。
  4. 数据量级为几百~几千件：全量文档（约 1000 × 平均 <300 字节）常驻内存仅 **数百 KB**，一次线性扫描 + 打分约 1–3 ms，**远优于 300ms 目标**。
- **索引数据结构**：`SearchIndex` 持有 `List<SearchDoc>`（见 [04-数据结构与接口.md](04-数据结构与接口.md)）。`SearchDoc` 在构建时已把「分类名 / 主位置路径各级名 / 全部存放位置名 / 标签名」**归一化后拼入**，因此单次查询只做**内存字符串操作，零 DB 往返**。
- **加载时机**：**不阻塞冷启动**。`SearchViewModel` 首次进入搜索页时，`stateIn` 拉取 `ItemRepository.observeSearchDocs()` 的最新快照构建 `SearchIndex`；后续仅当底层文档列表的**指纹（size + 最大 lastModifiedAt + 最大 createdAt）发生变化**时才重建，避免每次输入都重建。
- **输入即出结果的实现**：`query` 变化 → 在 `Dispatchers.Default` 上执行 `SearchIndex.query()` → 结果回主线程渲染；配合 `debounce(80ms)` + 取消上一个协程（`collectLatest`），保证流畅。
- **降级策略**：当**物品数 > 5000**（NFR-06 上限）时，仍走内存索引但强制 `limit=100` 并只在 `>=2` 个字符时触发；当**物品数 > 20000**（非家庭场景兜底）时，切换到 **SQL 兜底路径**：`WHERE normalizedName LIKE '%q%' OR aliasBlob LIKE '%q%' OR pinyinFull LIKE '%q%' OR pinyinInitials LIKE '%q%' LIMIT 200`（`LIKE '%x%'` 无法用索引，但 20k 行全表扫描仍在可接受范围），随后在内存做权重排序。降级开关由 `SearchConfig` 常量控制，便于压测调参。

### 2.4 拼音检索（FR-20 / Q8）

- **方案（已修正坐标）**：**houbb pinyin**，Maven 坐标 **`com.github.houbb:pinyin:0.4.0`**（**Maven Central 直取**，Apache-2.0，jar）。
  API：`PinyinHelper.toPinyin(text)`（全拼，`PinyinStyleEnum.NORMAL`）/ `PinyinHelper.toPinyin(text, PinyinStyleEnum.FIRST_LETTER)`（首字母），纯 Java、离线、无网络。
  > ⚠️ 坐标修正说明：初版误写为从旧 JCenter README 抄来的 `com.github.promeg:tinypinyin:2.0.3`，**该坐标在 JitPack 与 Maven Central 均返回 404、无法解析**；官方 TinyPinyin 在 JitPack 上只有 `com.github.promeg:tinypinyin:v2.0.3`（版本号带 `v`），且其 pom 会拖入 `tinypinyin-android-asset-lexicons` 等 AAR。故改用 Maven Central 上的 houbb pinyin。完整核验证据见 **[07-依赖包清单.md §6.7](07-依赖包清单.md)**。
- **包体积代价**：
  - houbb pinyin jar（含精简拼音词典资源）≈ **数百 KB 级**（R8 后更小）；另引入 2 个同作者小工具依赖 `com.github.houbb:heaven:0.2.0`、`com.github.houbb:nlp-common:0.0.5`（均 Apache-2.0）；
  - 对照（均实测可获得）：TinyPinyin 官方 `com.github.promeg:tinypinyin:v2.0.3`（**仅 JitPack**，且拖入 asset-lexicons AAR，体积与仓库风险更高）；`io.github.biezhi:TinyPinyin:2.0.3`（Maven Central 再发布，但 `packaging=pom` 非 jar、`<name>` 误写为 `redis-dqueue`、额外运行时依赖 `ahocorasick`，**判定不可信**）；`com.github.stuxuhai:jpinyin:1.1.8`（**GPL v3.0 许可**，法律风险，**否决**）；
  - 自建映射表：需维护 ~7000 汉字映射，准确率与长期维护风险高，不划算。
  - **结论**：选用 **`com.github.houbb:pinyin:0.4.0`**——唯一同时满足「Maven Central 可解析 + Apache-2.0 + 真 jar + 全拼/首字母 API」的选项；**因此不再需要 JitPack 仓库**（[07-依赖包清单.md §6.4](07-依赖包清单.md) 已删除该配置，等价于少一个构建失败点）。
- **生成/持久化时机**：**写入时预生成并持久化**（PRD Q8 默认值）——
  - 物品创建/更新（名称或别名变化）时，在 `ItemRepository` 的同一事务内计算并写入 `item.pinyinFull / pinyinInitials / aliasBlob`；
  - `item_alias` 每行也存自己的 `normalizedText / pinyinFull / pinyinInitials`（便于将来单独展示别名命中）；
  - 查询时**只做内存匹配**，不实时计算拼音（避免每次按键触发映射表查询）。
  - 不做声调、不做谐音纠错（[PRD 08 数据字段业务语义](../prd/08-数据字段业务语义.md) §7.6）。

### 2.5 DI 方案（NFR-03）

- **结论**：**Hilt 2.57.1（KSP）**。`hilt-android` + `ksp(hilt-android-compiler)`，配合 `androidx.hilt:hilt-navigation-compose:1.3.0` 提供 `hiltViewModel()`。
- **理由**：① 与 Room **共用同一 KSP 管道**，边际接入成本低；② **编译期**校验依赖图，缺失绑定直接编译失败（Koin 是运行期崩溃）；③ `@HiltViewModel` + `hiltViewModel()` 与 Compose/Navigation 原生集成，页面样板最少；④ **运行时开销 ~0**（容器代码预生成），不触碰冷启动 ≤1.5s（NFR-03）；⑤ `@TestInstallIn` 便于单测替换 Fake 仓库。
- **被否决**：
  - **Koin**：运行期解析依赖图（<100 绑定约 5–15ms，可接受但非零），无编译校验，多一个运行时库；对本项目收益低于 Hilt。
  - **手写 `AppContainer`**：零依赖、冷启动最优，但样板随规模膨胀、测试替换需手工接线。**作为最后回退方案保留**（若 KSP/Hilt 接入受阻，可在不改动 UI/Repository 的前提下替换为手写容器，因为 UI 只依赖 `@HiltViewModel` 注入的接口）。

### 2.7 分层与单向数据流（约定）

| 层 | 职责 | 禁止 |
|---|---|---|
| Screen（Composable） | 渲染 UiState、下发 `onXxx()` | 持有 Repository / 直接查 DAO / 写业务逻辑 |
| ViewModel | 持有 `StateFlow<UiState>`、编排用例、把异常映射为 UiState | 持有 Context（除 Application）/ 直接操作 DAO 事务 |
| Repository（接口） | 事务边界、聚合多 DAO、派生字段计算 | 暴露 DAO |
| DAO | 纯 SQL，`@Transaction` 组合 | 业务判断 |
| domain | 纯 Kotlin 模型 + 纯函数（打分/归一化） | 依赖 Android 框架 |

- **每个 ViewModel 的状态**（关键字段）：
  - `HomeViewModel`：`recentLocations`、`pendingCount`（待归位）、`incompleteCount`（待补）、`staleCount`（超期）、`totalItems`、`totalLocations`。
  - `SearchViewModel`：`query`、`filters`、`results: List<SearchHit>`、`recentSearches`、`isIndexing`。
  - `LocationTreeViewModel`：`tree: List<LocationNode>`（含 `expanded` 状态、`directCount`、`subtreeCount`）、`builtInIds`。
  - `LocationDetailViewModel`：`breadcrumb`、`directCount`/`subtreeCount`、`items`、`childLocations`、`isTemporary`。

  - `SettingsViewModel`：`thresholdMonths`、`onboardingDone`、`lastImportInfo`。

### 2.8 时间与状态机（[PRD 06 必须正面处理的难点](../prd/06-必须正面处理的难点.md) §5.2、FR-25/26/27、[PRD 08 数据字段业务语义](../prd/08-数据字段业务语义.md) §7.1）

**两个时间分别由哪些操作写入**（这是最容易实现错的地方）：

| 操作 | `lastModifiedAt`（最后变动） | `lastConfirmedAt`（最后确认） |
|---|---|---|
| 新建物品 | 写入 = now | **不动**（保持 NULL） |
| 点「确认还在」（单件） | **不动** | 写入 = now |
| 批量「全部确认还在」（按位置） | **不动** | 写入 = now（该位置子树内物品 + 相关 placement） |
| 移动位置 / 新增存放关系（改主位置） | **刷新 = now** | **不动** |
| 删除一条非主存放关系 | **刷新 = now**（归属变化） | **不动** |
| 状态变更（在存放中↔待归位，或 → 已丢弃/已送人/已用掉，或恢复） | **刷新 = now** | **不动** |
| 改名 / 改别名 / 改备注 / 改分类 / 改标签 / 改数量 | **不动** | **不动** |

> 一句话记忆：**只有「位置」和「状态」变化才动 `lastModifiedAt`；只有用户主动「确认还在」才动 `lastConfirmedAt`。**

**状态机存储类型**：存储为**稳定字符串 code**（不是 Int）：
`IN_STORAGE("in_storage")` / `TO_BE_PUT_BACK("to_be_put_back")` / `DISCARDED("discarded")` / `GIVEN_AWAY("given_away")` / `USED_UP("used_up")`。
- 理由：**向前兼容**——未来新增状态（如「已借出」）不会挪动既有值；导出 JSON 自解释；Room 用 `@TypeConverters` 做 `ItemStatus ↔ code` 映射（注意映射用 `code` 而非 `enum.name`，避免重命名常量破坏数据）。

**失效过滤**：所有「常规」查询默认带 `WHERE item.status IN ('in_storage','to_be_put_back')`；统计页 C-6「已失效物品」显式查 `IN ('discarded','given_away','used_up')`，并可恢复（`setStatus(IN_STORAGE)`）。

**「超期未确认」判定**（C-4 / FR-29 / Q10）：`lastConfirmedAt IS NULL OR lastConfirmedAt < now - thresholdMonths`，阈值默认 6，可配 3/6/12（存 `app_config.threshold_months`），**仅统计页展示，不发系统通知**（保持零权限）。

### 2.9 内置种子数据（Q9）

- **结论**：用 **`RoomDatabase.Callback.onCreate()`（首次建库回调）** 预置，**不用初始化迁移**。理由：种子只在**全新安装首次建库**时插入一次，`onCreate` 语义天然匹配；迁移方案会把「首次数据」与「结构演进」耦合，且在 DB 已存在的升级路径上多余。
- **实现要点**：回调内**必须用传入的 `SupportSQLiteDatabase.execSQL` 原始插入**（此刻 DAO 不可用，因为 DB 尚在创建中）；插入使用**固定哨兵 UUID**，便于导出/合并识别与「内置项」判定。
- **预置内容**：6–8 个内置分类（电器 / 衣物 / 工具 / 文具 / 药品 / 食品 / 清洁 / 其他）+ 2 个内置位置：`待归位区`（`isTemporary=1, isBuiltIn=1`，path=`/{id}/`）与 `未指定位置`（`isBuiltIn=1`）。
- **「内置项不可删但可改名」的实现**：`category.isBuiltIn` / `location.isBuiltIn` 标记；`CategoryRepository.delete` / `LocationRepository.deleteLocation` 在删除前检查，若 `isBuiltIn` 则返回 `DeleteResult.RejectedBuiltIn`，**UI 灰置删除入口**；改名走普通 `rename` 更新 `name`。`未指定位置`、`待归位区` 亦不可删、不可移入自身子树。
- **「家：客厅/卧室/…」位置模板（FR-07）**：`OnboardingViewModel` 读到模板选择后，调用 `LocationRepository.createLocation` 逐条建树（普通写路径，非种子），因此**可自由增删**，与内置位置区分开。

### 2.10 导出 / 导入（FR-42/43、NFR-10/11、Q5）

- **不申请存储权限**：全部走 **SAF**——
  - 导出：`ActivityResultContracts.CreateDocument("application/json")`（`ACTION_CREATE_DOCUMENT`），用户选择保存位置，应用 `ContentResolver.openOutputStream(uri)` 写入；
  - 导入：`ActivityResultContracts.OpenDocument(arrayOf("application/json"))`（`ACTION_OPEN_DOCUMENT`，带 `FLAG_GRANT_READ_URI_PERMISSION` 由系统授予）；
  - 分享：可选加 `ShareCompat`/`ACTION_SEND`（仍由用户主动触发，NFR-18）。
  - **不申请** `READ/WRITE_EXTERNAL_STORAGE`、`MANAGE_EXTERNAL_STORAGE`。
- **序列化选型**：**kotlinx-serialization-json 1.9.0**。理由：与 Kotlin 2.2.21 同源、**编译期生成序列化器（无反射）**、minSdk 24 无兼容问题、体积小；且**与导航类型安全路由共用同一编译器插件**（一处接入两处受益）。被否决：`org.json`（手写易错、无类型安全）、Moshi（反射/kapt、额外依赖）。
- **导出格式**：单一 **JSON**（`application/json`，`.shouna.json`），含 `schemaVersion`、`appVersion`、`exportedAt`，及 categories / locations / items / placements / aliases / tags / itemTags 全量。CSV 为辅为**下期**（Q5 默认），本期不做。
- **导入策略**：`ImportStrategy.OVERWRITE`（覆盖）/ `MERGE`（合并），**导入前弹出二次确认说明策略**（NFR-11）。
  - **OVERWRITE**：单事务内 `DELETE` 全部业务表（保留/重建内置项）→ 校验后 `INSERT`；
  - **MERGE**：以 **ID 为准 upsert**（同 ID 覆盖为文件内容；ID 不存在则插入；**不删除本地多余数据**）；因用 UUID，跨导出文件天然无冲突；
  - **失败回滚**：**先完整解析并做引用完整性校验**（每条 placement 的 itemId/locationId 必须存在；location.parentId 必须存在或为空；categoryId 允许空），**校验通过后才在 `database.withTransaction { }` 内写库**；任何异常 → 事务回滚，本地数据保持原样，向 UI 返回 `ImportResult.Failure(reason)`。

### 2.11 minSdk 24 的真实坑（重点）

- **结论**：**采用 core library desugaring + `java.time`**（`desugar_jdk_libs 2.1.5`）。理由：日期加减（+6 个月阈值）、"N 个月前"相对时间、"从未确认"判定用 `java.time` 语义清晰、bug 面小；体积代价可接受（Standard 变体，R8 后增量约 100–200KB）。
- **注意**：即使 DB 内只存 `Long`，只要**运行期**调用了 `java.time` API（格式化、加减、解析），API 24 设备上就必须 desugaring，否则 `NoClassDefFoundError`。`desugar_jdk_libs` 2.x 基于 JDK 11 源码，要求 **AGP ≥ 7.4.0**（本工程 8.13.2 ✓）。
- **minSdk 24 下其他 API 可用性核对**：
  - **Compose**：BOM 2025.12.01 的 `minSdk` 要求为 21，24 ✓；`enableEdgeToEdge()` 来自 `activity-compose 1.13.0`，24 ✓。
  - **Room**：minSdk 23 ✓；部分唯一索引（SQLite 3.8.0+）✓；`Flow` 查询用 Room 自带 `InvalidationTracker`，无版本限制。
  - **Navigation Compose 2.9.6**：minSdk 21 ✓；类型安全路由仅需 kotlinx-serialization（无 API 限制）。
  - **kotlinx-serialization**：minSdk 无关（纯 Kotlin）✓。
  - **houbb pinyin**：纯 Java（编译目标 1.7），无 API 限制 ✓。
  - **SAF**（`CreateDocument`/`OpenDocument`）：API 19+/19+ ✓。
  - **`java.util.UUID`**：✓。

### 2.12 「确认还在」的粒度（Q7）

- 物品级：`item.lastConfirmedAt = now`。
- 位置级批量（FR-28）：`LocationRepository.confirmLocationSubtree(locationId, now)` 在 **单个 `@Transaction`** 内执行 **2 条 UPDATE**（避免 N 次写）：
  1. `UPDATE placement SET lastConfirmedAt = :t WHERE locationId IN (SELECT id FROM location WHERE path LIKE :prefix) AND itemId IN (SELECT id FROM item WHERE status IN ('in_storage','to_be_put_back'))`
  2. `UPDATE item SET lastConfirmedAt = :t WHERE id IN (SELECT itemId FROM placement WHERE locationId IN (SELECT id FROM location WHERE path LIKE :prefix))`
  其中 `:prefix = location.path || '%'`（含自身，因为 `path` 含自身 ID）。两条语句均命中 `location.path`、`placement.locationId/itemId` 索引，复杂度近似 O(命中行数)。
- 返回受影响物品数，供 UI 显示「已确认 N 件」。

### 2.13 撤销 / 二次确认（NFR-12、FR-05）

- **统一交互**：所有破坏性操作（删位置 / 删分类 / 彻底删失效物品 / 删物品）**一律先弹 `ConfirmDialog`**；单条物品删除额外提供 **Snackbar「撤销」**（内存缓存被删行，5 秒内可回插；因 Q6 默认不做回收站，撤销是纯内存补偿）。
- **删位置的两条路径（FR-05，禁止孤儿）**：`deleteLocation(id, mode, migrateTargetId)`
  - **CASCADE_DELETE_ITEMS（其下物品一并删除）**：单事务内——删除子树内所有 `placement`（`WHERE locationId IN subtree`）→ 删除子树内所有 `item`（连带 `alias`/`item_tag` 级联）→ 自底向上删除子树内所有 `location`。
  - **MIGRATE_ITEMS（迁移到指定位置）**：校验 `migrateTargetId` **不在被删子树内**（否则拒绝）→ 单事务内 `UPDATE placement SET locationId = :target WHERE locationId IN subtree`（若迁移后物品在该目标处已存在 placement，则合并数量/保留一条并删重复，避免复合主键冲突）→ 迁移后若某物品失去主位置则提升 → 删除子树 `location`。
  - **孤儿防线**：`placement.locationId` 外键 `ON DELETE CASCADE` 作为**安全网**；`location.parentId` 用 `ON DELETE RESTRICT` **禁止隐式级联**，强制由 Repository 显式、自底向上删除，杜绝「子位置悬空」。
- **删分类**：`ON DELETE SET NULL`，物品转「未分类」，**不丢物品**（FR-44）；内置分类拒绝删除。

### 2.14 位置树读取性能（NFR-07、FR-21）

- **结论**：**持久化物化路径 `location.path`（ID 序列）作为结构索引** + **应用层内存树**用于 UI 渲染。
  - 递归计数（FR-21「本层 N 件 / 含子层共 M 件」、C-3 Top N）：**SQL 一条聚合**——`JOIN placement ON placement.locationId IN (SELECT id FROM location WHERE path LIKE :prefix)` `GROUP BY locationId`，或用 `substr` 拼接。500 节点的树，一次遍历 + 一次聚合在毫秒级。
  - UI 展开/滚动：`LocationTreeViewModel` 一次性加载全部位置（500 行 < 100KB）构建**内存树**，`LazyColumn` + `key` 复用，展开/收起纯内存操作，**不给每帧打 DB**。
- **面包屑（位置路径）是派生字段**：
  - **展示用面包屑（名称路径）= 派生**，由父链在内存中拼出（[PRD 08 数据字段业务语义](../prd/08-数据字段业务语义.md) §7.2 明确「由父链推导，不手工维护」）；
  - 额外**持久化**的是**结构用 `path`（ID 序列）**，它**不是**面包屑，只服务「子孙范围查询」，避免递归 CTE。
- **迁移动子树时维护 `path`**：`UPDATE location SET path = :newPrefix || substr(path, length(:oldPrefix) + 1), depth = depth + :delta WHERE path LIKE :oldPrefix || '%'`（含自身），一条语句批量更新；同时**校验不能把节点移入自身子孙**（对应 `path LIKE` 判定）。
- **被否决**：递归 CTE（SQLite 3.8.3+ 可用但每次查询需递归，且路径展示仍需应用层拼装）；纯应用层内存树做统计（全表加载后计算，随规模退化，且统计页与树页耦合）。

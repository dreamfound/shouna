## 7. 数据字段层面的关键定义建议（业务语义层）

> 本节只描述**业务语义与必填性**，不涉及表结构/类型/索引（由架构师决定物理实现）。

### 7.1 物品（Item）

| 业务字段 | 含义 | 必填 | 说明 |
|---|---|---|---|
| 名称 | 用户对这件东西的称呼 | **必填** | 唯一性**不强制**（允许同名，靠位置区分） |
| 别名 / 俗称 | 其他常见叫法（多个） | 可选 | 参与检索，例如「电风扇」的别名「风扇」「电扇」 |
| 检索键 | 由名称+别名派生的拼音全拼与拼音首字母 | 派生 | 自动生成，用户不可见 |
| 分类 | 归属分类（引用分类实体） | 可选 | 未填视为「未分类」 |
| 标签 | 多个自定义标签 | 可选 | 参与检索 |
| 数量 | 件数 | 可选 | 默认 1；本期仅支持整数，不做单位换算 |
| 状态 | `在存放中 / 待归位 / 已丢弃 / 已送人 / 已用掉` | **必填** | 默认「在存放中」 |
| 备注 | 自由文本 | 可选 | 如「遥控器在侧袋」 |
| 创建时间 | 首次录入时间 | **必填**（系统） | 系统写入 |
| 最后变动时间 | 最近一次归属或状态发生变动的时间 | **必填**（系统） | 仅「位置/状态」变动才刷新 |
| 最后确认时间 | 最近一次用户主动确认「还在」的时间 | 可空 | 从未确认为空，需在 UI 上区分「从未确认」与「很久没确认」 |
| 信息完整度 / 待补详情 | 是否为需要事后补录的不完整记录 | 派生（查询期计算，不落库） | **唯一判定口径见本文件「7.1.1」**，供 FR-13 与统计卡片 C-7 使用 |

#### 7.1.1 「待补详情 / 信息完整度」的唯一判定口径（架构约束 A-4 结论）

**判定规则（满足任一即为「待补详情」）**

| 条件 | 表述 |
|---|---|
| 条件 ① | 物品**未填分类**（分类为空） |
| 条件 ② | 物品的**主位置**是内置的「未指定位置」 |

**可直接翻译成查询条件的写法**

```
待补详情 = ( item.categoryId IS NULL )
        OR ( 主位置(该 item 上 isPrimary 的存放关系).locationId == 内置「未指定位置」的 ID )
```

**明确排除**（下列为空**不算**待补详情）：别名、标签、备注、数量。

**为什么把口径定得这么窄（重要权衡）**

1. **这两项才是「缺了就真的用不了」的信息**：分类决定归纳/统计（[09-归纳汇总.md](09-归纳汇总.md) 的 C-2、C-7）能不能算出有意义的结果；主位置决定搜索能不能直接给出「东西在哪」的答案。缺了这两项，核心价值闭环是断的。
2. **口径过宽会反噬用户**：如果连「无别名 / 无标签 / 无备注 / 数量为空」都算待补，那么按极简录入（[06-必须正面处理的难点.md](06-必须正面处理的难点.md) 的 M-3「只填名称即可保存」、M-5「草稿箱」）创建的记录，**100% 一落地就是「待补详情」**。用户一进统计页就看到「你有 80 件待补」——提醒立刻变成指责，用户会直接无视这个数字，甚至连真正该补的记录也不再理会。这与 [06-必须正面处理的难点.md](06-必须正面处理的难点.md)「压低录入成本、别让 App 变成负担」的初衷直接冲突。
3. **窄口径可闭环**：用户补上分类、指定好位置，这个数字就能**归零**，获得「我把它收拾干净了」的正反馈。宽口径永远无法归零，也就永远没有完成感。
4. **实现一致性**：该判定必须**只依赖分类与主位置**两条，不得再引入其它字段，否则 C-1 与 C-7 的数字会与用户直觉不符。

**由此产生的可验证行为**：别名/标签/备注/数量无论是否填写，**都不改变**「待补详情」判定；统计页的待补数量随用户补分类、补位置而**单调下降**。

### 7.2 位置（Location）

| 业务字段 | 含义 | 必填 | 说明 |
|---|---|---|---|
| 名称 | 位置称呼（储物间、纸箱-07） | **必填** | 同一父级下**应用层软校验**不得重名，**非数据完整性约束**（见下方说明） |
| 父位置 | 上级位置引用，根位置为空 | 可选 | 支持任意层级；根节点可为「家」 |
| 路径 | 从根到当前的完整路径（派生） | 派生 | 用于面包屑与复制；由父链推导，不手工维护 |
| 类型标签 | 房间 / 柜子 / 箱子 / 格 / 其他 | 可选 | **仅视觉标记**，不做强约束 |
| 是否临时 | 是否为「临时/待归位区」 | 可选 | 默认否；系统内置一个「待归位区」 |
| 备注 | 自由文本（如「最底层靠墙」） | 可选 | — |
| 排序序号 | 同级展示顺序 | 可选 | 默认按创建顺序 |
| 创建时间 | 系统写入 | **必填**（系统） | — |

**「同级不重名」的校验语义（架构约束 A-3 结论）**

- 这是**应用层的软校验**，不是数据库层的强约束。用户新建或重命名位置时，应用比对**同一父级**下已有名称，若重名给出**提示**（建议改为「纸箱-07」「纸箱-07(2)」），但**允许用户坚持使用重名**。
- **不要让实现方误以为数据库唯一约束能兜底**：即使采用 `UNIQUE(父级, 名称)` 之类的约束，它对**根级位置也不生效**——SQLite 的唯一索引对 `NULL` 不判重，而根级位置的「父级」正是空值。因此**根级重名只能靠应用层拦截**，数据库层不会报错、也拦不住。
- 结论：重名提示是**体验优化**，不是**数据完整性要求**。即使出现重名，系统行为必须保持正确——**一切以 ID 区分，绝不靠名称作为标识**。因此本项**不允许**被写成「架构保证」或「数据库保证」。

### 7.3 「物品存在于某位置」的关系表达（重点）

**结论：本期即按「多对多」建模，但 UI 默认只暴露「一个主位置」。** 这样既能满足「一件物品分散在多处」（如 10 卷胶带分别放在厨房和储物间），又不会让普通用户在录入时被迫做复杂选择。

**存放关系（Placement）语义字段**

| 业务字段 | 含义 | 必填 | 说明 |
|---|---|---|---|
| 关联物品 | 指向物品 | **必填** | — |
| 关联位置 | 指向位置 | **必填** | — |
| 是否主位置 | 是否为该物品的「主存放位置」 | **必填** | 每件物品**有且仅有一个**主位置；搜索结果显示主位置路径 |
| 该处数量 | 该位置上的件数（分摊数） | 可选（**为空 = 继承总数量**） | **为空则展示为物品总数量；非空则为此处分摊数**；不强制各处之和等于总数量，见本文件「7.3.1」 |
| 位置备注 | 该处的具体说明（如「侧袋里」） | 可选 | — |
| 该处最后确认时间 | 针对**这一处**的确认时间 | 可空 | 支持「我只确认了储物间那箱，没确认厨房那卷」 |
| 建立时间 | 系统写入 | **必填**（系统） | — |

**约束建议**
- 一件物品至少有一条存放关系（否则归入内置「未指定位置」）。
- 主位置唯一；把某处设为主位置时，原主位置自动降级。
- 物品被标记为 `已丢弃/已送人/已用掉` 时，其存放关系**保留**（不物理删除），仅在常规查询中过滤。

#### 7.3.1 多处存放时的数量语义（架构约束 A-5 结论）

| 字段 | 语义 |
|---|---|
| `物品.数量` | **总数量**（顶层概念），默认 1 |
| `存放关系.该处数量` | **为空** → 该处显示数量 = 物品总数量（用户没有细分）；**非空** → 该处数量 = 用户填写的分摊数 |

**规则（可直接翻译成实现与校验）**

1. `物品.数量` 表示「这件东西一共有多少」；`该处数量` 只描述「这一处放了多少」。
2. `该处数量` 为空时，**展示层按总数量显示**，**不写回、不落库**（保持为空即为继承语义）。
3. **不强制「各处数量之和 = 总数量」**，**不做任何校验报错、不做自动补差**。
4. **为什么不强制（必须写进文档的理由）**：强制求和一致，会逼用户在多处存放时逐处填写精确数字，并处理余数——这**直接挡住极简录入路径**：与 [06-必须正面处理的难点.md](06-必须正面处理的难点.md) 的 **M-1「先选位置再连续录」**、**M-3「只填名称即可保存」**、**M-5「草稿箱」** 全部冲突。用户的真实心智是「厨房大概 5 卷、储物间还有几卷」，**允许不精确，远好过逼用户放弃记录**。这与本 App 的头号死因（录入成本）直接相关。
5. 因此**统计口径以 `物品.数量` 为准**（件数统计），`该处数量` 只用于位置维度的**参考展示**；即使某个位置的分摊数缺失，也不影响任何统计的正确性。
6. 单处存放（覆盖绝大多数真实场景）时，`该处数量` 恒为空，数量语义**退化为一对一的直觉模型**，用户完全感知不到「多对多」的存在。

### 7.4 分类（Category）

| 业务字段 | 含义 | 必填 | 说明 |
|---|---|---|---|
| 名称 | 分类名 | **必填** | 同级不重名 |
| 图标 / 颜色 | 视觉标识 | 可选 | 便于快速点选（FR-12） |
| 是否内置 | 是否为系统预置 | 派生 | 内置项可改名但建议不可删 |
| 排序序号 | 展示顺序 | 可选 | — |

**规则**：删除分类时，其下物品**不删除**，统一转「未分类」。

### 7.5 标签（Tag）

| 业务字段 | 含义 | 必填 | 说明 |
|---|---|---|---|
| 名称 | 标签名 | **必填** | 全局唯一（不区分大小写） |

### 7.6 检索字段的业务要求（名称 / 别名 / 拼音首字母）

| 要求 | 说明 |
|---|---|
| **多字段并检** | 一次搜索须同时覆盖：物品名称、物品别名、拼音全拼、拼音首字母、分类名、位置名（含路径各级）、标签 |
| **拼音能力** | 离线内置，支持全拼（`dianfengshan`）与首字母（`dsf`）；不做声调、不做谐音纠错 |
| **归一化** | 忽略大小写、忽略全角/半角差异、忽略首尾与连续空格 |
| **匹配方式** | 子串包含匹配（`name contains q`），非精确匹配；结果按「名称前缀命中 > 名称子串命中 > 别名/拼音命中 > 位置/分类命中」排序 |
| **位置名搜索的连带效果** | 搜「储物间」应能列出该位置**递归**下的所有物品 |
| **高亮** | 结果列表高亮命中片段 |
| **性能** | 1000 件物品响应 ≤ 300ms；5000 件 ≤ 800ms（见 [10-非功能需求.md](10-非功能需求.md)） |
| **无网络** | 全部本地计算，不依赖任何在线服务 |
| **检索键的持久化边界（架构约束 A-2）** | **只有「物品名称 + 别名」派生的检索键**（归一化名称 / 全拼 / 首字母 / 别名拼接）**持久化在物品记录上**。**位置名（含路径各级）、分类名、标签名一律不冗余写入物品记录**，而是在构建检索数据时**实时关联拼入**内存。 |

**为什么位置名 / 分类名 / 标签名不做冗余持久化（架构约束 A-2 结论）**

- 位置名会**被重命名**、位置会**整体移动**（整棵子树搬家）；分类名、标签名也可能被改名。
- 如果把这些名称**冗余写进每一条物品记录**：
  1. **写放大严重**——改一次名，需要重写**所有**关联物品记录；
  2. **必然出现不一致**——只要漏改一处（例如移动子树时只更新了位置自身的路径，忘了刷新物品记录），搜索就会出现「**命中不到**」或「**命中到旧名字**」的脏结果，且极难排查。
- 因此本 PRD 明确规定：**物品记录上只持久化「名称 + 别名」派生的检索键**；位置名、分类名、标签名在**构建检索文档时实时关联拼入内存**。改名 / 移动只需要改位置、分类、标签自身，检索数据**自动跟随**。
- 收益：改名与移动的代价**与物品数量脱钩**（近似 O(1)），检索结果**永远与当前名称一致**。
- **对用户可见行为零影响**：搜索依然能命中位置名与分类名（FR-19、FR-21 的要求不变），只是实现方式从「冗余存储」改为「构建时关联拼入」。验收口径仍是「搜『储物间』能列出该位置递归下的所有物品」。
